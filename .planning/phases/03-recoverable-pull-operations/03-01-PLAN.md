## Phase Goal

**As a** vault operator, **I want** displaced or remotely deleted files to be safely archived into an external, collision-safe quarantine store before local removal, **so that** my data is never destroyed by uncoordinated remote deletions and pull operations maintain crash-safe state outside the vault.

<objective>
Implement the storage foundation and collision-safe quarantine mechanism:
1. SQLite migrations 003 (`quarantine` table) and 004 (`pull_checkpoints` table).
2. `QuarantineRepository` and `CheckpointRepository` data access classes.
3. Extended `ProvenanceRepository` with deletion and full map querying.
4. Fail-closed `quarantineVaultFile` function with byte-level read-back verification and atomic unlink gating.

Purpose: Provide the durable storage and file-preservation primitives required for recoverable pull and deletion reflection.
Output: Tested storage migrations, repositories, and quarantine file operations.
</objective>

    - Reads source vault file, computes sha256, writes to quarantine directory, and performs read-back byte verification
    - Saves record in QuarantineRepository
    - Unlinks source vault file only after verification and DB write succeed

       - Export function `quarantineVaultFile(vaultRoot, stateRoot, relativePath, remoteRevision, quarantineRepo, options?)`:
         - Call `assertSafeVaultRelativePath(relativePath)`.
         - Read file bytes from `join(vaultRoot, relativePath)`.
         - Compute `hash = createHash('sha256').update(fileBytes).digest('hex')`.
         - Format timestamp `new Date().toISOString().replace(/[:.]/g, '-')`.
         - Construct `safeSubdir = ${timestamp}_${hash.slice(0, 8)}` and `destQuarantinePath = join(stateRoot, 'quarantine', safeSubdir, relativePath)`.
         - Ensure destination directory exists via `mkdir(dirname(destQuarantinePath), { recursive: true })`.
         - Write `fileBytes` to `destQuarantinePath`.
         - Read back bytes from `destQuarantinePath` and assert byte-for-byte equality against `fileBytes`.
         - Call `quarantineRepo.saveQuarantine({...})`.
         - Call `unlink(join(vaultRoot, relativePath))`.
         - Return the `QuarantineRecord`.
         - Support injectable `readFileFn`, `writeFileFn`, and `unlinkFn` in options for reliable fault-injection unit testing.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| File paths from remote / local | Untrusted relative path strings could attempt directory traversal (`../../`) to escape vault or quarantine directories |
| Quarantine destination filesystem | File write or copy operations could partially fail due to disk exhaustion or permission errors |
| SQLite database files | External metadata state stored outside the vault namespace must never contain secrets or credentials |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-01 | Elevation of Privilege / Tampering | quarantineVaultFile / path-policy | high | mitigate | Use `assertSafeVaultRelativePath` before constructing any quarantine path; paths with `..` or absolute prefixes are rejected |
| T-03-02 | Data Loss / Denial of Service | quarantineVaultFile | high | mitigate | Fail-closed quarantine: read-back verify copied bytes and insert SQLite row before calling `unlink`; if any step fails, abort and preserve original vault file |
| T-03-03 | Information Disclosure | QuarantineRepository / CheckpointRepository / SQLite | medium | mitigate | SQLite schema explicitly excludes passphrases, tokens, or plaintext note bodies; stores only hashes, paths, revisions, and update_seq |
| T-03-04 | Repudiation | QuarantineRepository | low | mitigate | Quarantine table durably logs `original_path`, `quarantine_path`, `remote_revision`, `content_sha256`, `reason`, and `quarantined_at` |
</threat_model>
